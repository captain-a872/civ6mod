# 工作流程

本文件约定讨论、文档与 Git 的工作方式。**与《项目指令.txt》冲突时，以项目指令为准。**

## 一、阶段定义

| 阶段 | 状态 | 说明 |
|------|------|------|
| 设计阶段 | ✅ **当前** | 逐模块产出策划案；**不编写任何 mod 代码** |
| 实现阶段 | 未启动 | 由项目所有者明确宣布启动后，才开始 mod 实现 |

**设计→实现的切换权仅在项目所有者。** 助手不得因"策划看起来完整了"而主动提议开工。

## 二、讨论工作流（每轮对话）

1. **指定模块**：所有者指明本轮讨论的模块；未指定时不得擅自跳到未讨论模块
2. **回顾总案**：讨论前先读《设计总案》回顾既有结论，避免推翻已定决策
3. **推进顺序**：模块内部按"核心幻想 → 核心机制 → 支撑系统 → 数值框架"推进
4. **输出格式**：方案对比 + 推荐意见，关键机制至少给出 2 个备选方案并说明取舍
5. **批量文本**：大段内容写文件传达，不在对话中整段贴出
6. **有疑问先问**：不确定或信息不足时，先提问到获得答案再执行
7. **更新总案**：每轮讨论结束后，将确认的结论更新到总案对应模块（由助手执行）

## 三、文档管理

| 文件 | 更新责任人 | 更新时机 |
|------|-----------|---------|
| 项目指令.txt | 所有者 | 需要时 |
| 设计总案.md | 助手 | 每轮讨论结束后 |
| 模块策划案.md | 助手（经所有者确认后） | 该模块讨论有阶段性结论时 |
| 工作流程.md | 双方共识后 | 工作方式变更时 |

- 策划案版本号：重大框架调整升主版本（v1.x → v2.0），局部修订升次版本（v1.1 → v1.2），文件头部注明"基于总案 vX.X"
- 已确认决策只追加、不静默修改；需要推翻时必须显式说明并记录原因

## 四、Git 工作流

- **单分支**：`main`，直接提交（设计阶段变更频率低，暂不引入分支模型）
- **提交信息规范**：`docs(模块): 摘要`，例如：
  - `docs(总案): 确认比例尺语义为精细度而非世界尺寸`
  - `docs(模块1): 地形参数表补充山口防御加力`
- **推送时机**：每轮讨论结束、文档更新完毕后立即提交推送

## 五、实现阶段启动条件（备忘）

满足以下条件时，所有者可宣布进入实现阶段：

1. 模块1+2 策划定稿（总案决策#3：先定框架地基）
2. 明确实现顺序与分期（已预确认的方向：骨架+水文 → 群系+资源 → 灾害+可视化）
3. 比例尺性能验证方案确定（1:4/1:9 细化地图的生成性能、存档体积、回合耗时）
4. 新地形视觉策略确定（已预确认：美术暂不考虑，复用原版贴图）

## 六、决策速查（最近更新 2026-09-27）

- ✅ 比例尺 1:4/1:9 = 精细度细化，非世界放大（可同尺寸更精细）
- ✅ 美术资产暂不考虑，数据先行
- ✅ 模块1实现分三期：骨架+水文 / 群系+资源 / 灾害+可视化
- ✅ AI 第一版仅保证不崩 + 合理 fallback，深度适配后置
- ⏸️ 模块1仍在讨论中，禁止实现
