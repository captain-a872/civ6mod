# 工作流程

本文件约定讨论、文档、Git 与多 Agent 协作的工作方式。**与《项目指令.txt》冲突时，以项目指令为准。**

## 一、阶段定义

| 阶段 | 状态 | 说明 |
|------|------|------|
| 设计阶段 | ✅ 模块1设计闭环（2026-09-28，v1.11） | 逐模块产出策划案；模块1文档闭环，模块2起进入设计轮次 |
| 实现阶段 | ✅ **已启动**（2026-09-28 所有者宣布，模块1试做） | 要求：可在游戏内运行；分期见 docs/模块1-实现计划.md |

**设计→实现的切换权仅在项目所有者。** 助手不得因"策划看起来完整了"而主动提议开工。

## 二、讨论工作流（每轮对话）

1. **指定模块**：所有者指明本轮讨论的模块；未指定时不得擅自跳到未讨论模块
2. **回顾总案**：讨论前先读《设计总案》回顾既有结论，避免推翻已定决策
3. **推进顺序**：模块内部按"核心幻想 → 核心机制 → 支撑系统 → 数值框架"推进
4. **输出格式**：方案对比 + 推荐意见，关键机制至少给出 2 个备选方案并说明取舍
5. **批量文本**：大段内容写文件传达，不在对话中整段贴出
6. **有疑问先问**：不确定或信息不足时，先提问到获得答案再执行
7. **更新总案**：每轮讨论结束后，将确认的结论更新到总案对应模块（由助手执行）

## 三、多 Agent 编排

> 2026-09-27 试点（v1.3 审查：3 个并行审查 Agent 信息源不重叠，抓出主控单线程几乎必然漏掉的跨文档问题）后确立，为本项目标准协作流程。

### 3.1 角色与职责

| 角色 | 承担者 | 职责 | 是否并行 |
|------|--------|------|---------|
| 主控 | Kimi 对话本体 | 任务切分、汇总裁决、验收、Git 提交、与所有者对话 | — |
| 审查 Agent × N | 子代理（explore） | 按任务单对文档/资料做**只读**审查，输出报告写入 `docs/reviews/` | ✅ 彼此并行 |
| 修订 Agent | 子代理（coder） | 按已裁决的清单执行文档修订 | ❌ 串行，同一时刻只跑一个 |
| 技术调研 Agent | 子代理（explore） | 对单一外部问题（API、先例、机制可行性）做深入查证 | ✅ 可与审查并行 |

### 3.2 标准流水线

```
① 主控定任务单 → ② 并行审查/调研 Agent → ③ 主控汇总（严重度分级）→
④ 所有者裁决 → ⑤ 修订 Agent 逐条落实 → ⑥ 主控验收 → ⑦ commit & push
```

- **① 任务切分原则**：多审查并行时，信息源必须不重叠（如 2026-09-27 试点切分为"概念残留 / 技术调研 / 决策对齐"三份，各读不同材料、答不同问题）
- **③ 汇总**：主控将发现按 🔴需所有者裁决 / 🟡可直接修订 / 🟢信息项 分级；**裁决权在所有者**，主控只给推荐意见
- **⑤ 修订**：修订 Agent 的 prompt 必须包含完整背景、精确文件路径、逐条清单（含建议改法）、禁改范围；"建议改法与上下文冲突时自行判断并记录"写入 prompt
- **⑥ 验收**：结构性改动（重建表格/章节）必须抽查原文；机械性清单用 grep 验证残留清零；验收不过则带具体意见 resume 修订 Agent 返工

### 3.3 调度规则（何时派、何时不派）

| 场景 | 决策 |
|------|------|
| 修订点 ≥ 10 处或含结构性重建 | 派修订 Agent |
| 跨文档一致性审查 / 多源调研 | 派并行审查 Agent（≥2 个，切分信息源） |
| 小于 5 处的精确小编辑 | 主控直接改，不派 Agent |
| 总案级小手术（挪章节、加决策行） | 主控直接改 |

- 子代理零上下文启动：prompt 须自带全部背景与路径，不得让它猜
- **写入者唯一**：同一文件同一时刻只有一个写入者（主控或某个修订 Agent）
- 审查（只读）与修订（写入）不并行；修订依赖审查结论
- 子代理一律不得执行 `git commit/push`，提交归主控

### 3.4 实证记录

- 2026-09-27 v1.3 审查：3 并行审查 Agent → 25~29 处概念残留、海拔持久化调研（风险降级）、决策对齐 3 裁决点
- 2026-09-28 v1.4 修订：1 修订 Agent 落实 24 行清单 + 3 项裁决 → 主控验收通过（grep 残留清零 + 结构抽查）

## 四、文档管理

| 文件 | 更新责任人 | 更新时机 |
|------|-----------|---------|
| 项目指令.txt | 所有者 | 需要时 |
| 设计总案.md | 助手 | 每轮讨论结束后 |
| 模块策划案.md | 助手（经所有者确认后） | 该模块讨论有阶段性结论时 |
| 工作流程.md | 双方共识后 | 工作方式变更时 |

- 策划案版本号：重大框架调整升主版本（v1.x → v2.0），局部修订升次版本（v1.1 → v1.2），文件头部注明"基于总案 vX.X"
- 已确认决策只追加、不静默修改；需要推翻时必须显式说明并记录原因
- 审查报告归档于 `docs/reviews/<日期>-<主题>/`，命名 `A-主题.md`、`B-主题.md`…

## 五、Git 工作流

- **单分支**：`main`，直接提交（设计阶段变更频率低，暂不引入分支模型）
- **提交信息规范**：`docs(模块): 摘要`，例如：
  - `docs(总案): 确认比例尺语义为精细度而非世界尺寸`
  - `docs(模块1): 地形参数表补充山口防御加力`
- **推送时机**：每轮讨论结束、文档更新完毕后立即提交推送

## 六、实现阶段启动条件（备忘）

满足以下条件时，所有者可宣布进入实现阶段：

1. 模块1+2 策划定稿（总案决策#3：先定框架地基）
2. 明确实现顺序与分期（已预确认的方向：骨架+水文 → 群系+资源 → 灾害+可视化）
3. 比例尺性能验证方案确定（1:4 细化地图的生成性能、存档体积、回合耗时；六边形格数口径见模块1附录注记）
4. 新地形视觉策略确定（已预确认：美术暂不考虑，复用原版贴图）
